--- Q3/25 [A3] How is delivery actually done?
    latency_s=27.1 manifest=/home/liam/agentic-os-live/queue/context_assemblies/hermes-20260906_171954_7c24e0-20260906_171954_7c24e0:5fcf406c-efd9-48b8-8255-240999470fde:8fbd5c67.json
    ANSWER: Delivery is not “make a plan, hand over recommendations.”

It is done as a scoped implementation workflow inside the client’s real operation, with evidence at every stage.

The actual pattern is:

1. Intake and scope
   - You need a client entity page.
   - You need signed scope / agreed delivery contract.
   - You need a client-isolated folder.
   - If those are missing, delivery should refuse to start.

2. Map the real workflow
   - Where does the work happen today?
   - What tools, people, handoffs, messages, forms, inboxes, spreadsheets, CRMs, or calls are involved?
   - What falls through?
   - What is slow, duplicated, invisible, or ownerless?

3. Get client agreement on the target design
   - Not a big theoretical architecture.
   - A concrete “here is how this workflow will run after the build.”
   - Approval gates are marked.
   - Human-in-the-loop points are explicit.
   - Anything external-facing or mutating client systems remains gated.

4. Build the system
   - Implement the scoped workflow: automations, scripts, CRM fields, docs, handoff rules, dashboards, AI support, or whatever the real bottleneck needs.
   - Use Codex / Claude / workbenches where useful.
   - But delivery remains responsible for the outcome, not the worker.

5. Test against reality
   - No “looks good.”
   - A test lead, test case, or real business question must traverse the system.
   - Evidence is recorded: logs, screenshots, output files, timestamps, acceptance notes.
   - If the system is supposed to improve speed-to-lead, a test lead must actually move through every scoped inbound path.
   - If it is client memory, claims must trace to sources and answer real business questions correctly.

6. Handoff
   - Client gets practical docs:
     - what it does
     - how to use it
     - what it never does automatically
     - how to pause/rollback
     - who owns updates
   - This matters because renewal depends on the client seeing usable operating capability, not being impressed once.

7. Closeout
   - Update the client entity page.
   - Write the receipt.
   - Record token / work evidence.
   - Revoke or close unnecessary access.
   - Preserve client isolation.

The simplest summary:

Delivery = scoped workflow repair, built in the client’s context, tested with real acceptance evidence, handed off so the client can run it.

The current offer shapes implied by the system are:

- Quick-Win Scan: diagnostic, one bottleneck, one fix, no implementation.
- Speed-to-Lead Build: inbound capture → route → respond → follow-up.
- Client Memory Build: source-backed knowledge base their AI/tools can safely use.
- AI Operations Support: monthly retainer cycle, session prep/follow-up, hub updates, ongoing operational visibility.

My interpretation: the strongest delivery motion for TTR right now is not bespoke “AI consulting.” It is repeatable forward-deployed builds around revenue leakage and operational memory, starting small enough to close, but concrete enough to become a paid implementation proof.

The danger: if delivery becomes another internal OS abstraction, it fails. The client should experience it as, “this broken workflow now works,” not “Liam has an impressive agent system.”
