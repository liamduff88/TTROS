--- Q3/25 [A3] How is delivery actually done?
    latency_s=36.2 manifest=/home/liam/agentic-os-live/queue/context_assemblies/ctx-017479d3e3024366ae9273224a2b784f.json session_id=20260909_190308_af193c
    ANSWER: Delivery is not “we advise, then disappear.”

It is done as a forward-deployed engineering engagement:

1. Start with a real client workflow

Not a generic automation brief.

Examples:
- inbound lead response
- transaction/document tracking
- scattered client knowledge
- post-call follow-up
- sales/admin handoff
- reporting visibility

The unit of delivery is one operating workflow with a clear before/after.

2. Confirm the contract before building

For a proper build, delivery needs:
- client entity page
- signed scope or explicit agreed pilot boundary
- isolated client folder/hub
- source/data sensitivity classification where relevant
- definition of done
- approval gates for anything external-facing

If those are missing, delivery should stop or stay as a draft/prototype.

3. Map current reality

First deliverable is usually a map:

“Here is how this work happens today.”

For example:
- where leads come from
- who receives them
- where they get lost
- what gets manually copied
- what documents or fields are checked
- what approval is required
- what the client already uses
- what must not be automated

This matters because TTR sells removal of operational friction, not software for its own sake.

4. Design the target workflow

Then design the smallest better system:

capture → route → decide → act → record → review

The design must say:
- what the system does
- what humans still approve
- what it never does automatically
- where the client sees status
- what evidence proves it worked

For client work, this stage should usually require client sign-off before implementation.

5. Build inside the client’s actual context

This can mean:
- Sheets / Airtable / Notion / CRM configuration
- Make/Zapier/GHL workflows
- lightweight scripts
- dashboards
- inbox/lead capture rules
- client knowledge base
- AI-assisted draft generation
- manual-review queues

The point is not “AI.” The point is a working operating system for that workflow.

6. Test with real acceptance evidence

Done is not “it runs on my machine.”

Done means the agreed workflow has been exercised.

Examples:
- a test lead enters every scoped inbound path and reaches the right place inside the target response time
- a client can ask “which transactions are missing these forms?” and the tracker answers correctly
- sample knowledge-base claims trace back to source documents
- handoff rules are visible and understood
- screenshots/logs/test records are saved

No evidence, no done.

7. Handoff and make it maintainable

The client gets:
- what it does
- how to use it
- how to pause it
- how to update it
- what still requires human approval
- known limits
- support path

For retainers, the client hub must stay current. That is the renewal asset.

8. Close with receipt and access cleanup

Internally, delivery closes with:
- updated client/entity page
- output artifact
- receipt
- token/time breakdown where relevant
- closeout checklist
- access revoked or reduced where the scope is complete

My blunt read:

TTR delivery should be sold and run as “we embed, map one painful workflow, build the working fix, prove it with acceptance evidence, and leave you with a maintainable operating asset.”

The current weak point is not the delivery model. The weak point is that Liam does not yet have enough paid implementation proofs. So the next delivery motion should be deliberately small: one workflow, one client, one visible operational win, one receipt-quality proof.

--- Q4/25 [A4] What are we not allowed to claim to a prospect?

    ANSWER: We are not allowed to claim anything to a prospect that we cannot evidence.

Specifically, do not claim:

1. Client results
   No “we increased revenue,” “we saved X hours,” “we improved conversion,” or case-study-style outcomes unless we have sourced proof.

2. Revenue figures or ROI numbers
   No promised, implied, or projected ROI as if achieved. Fit-call prep explicitly says: do not promise ROI numbers.

3. Case studies
   No invented or composite case studies. If a case note exists, every claim must be sourced; anonymized versions must not leak client identity.

4. Credentials, partnerships, or authority we have not earned
   No industry credentials, partner status, certifications, named relationships, or implied institutional backing unless evidenced.

5. Proprietary methods
   No “proprietary system/method/framework” unless there is a real, evidenced method and we are prepared to stand behind the wording.

6. Vertical expertise TTR has not yet earned
   We can say we work on operational friction in growing service businesses. We should not claim deep vertical expertise in an industry before we have proof.

7. Track record beyond what TTR has actually built
   We can describe the operating model and what TTR is building/proving on itself. We cannot imply a mature forward-deployed engineering or GTM engineering track record that does not yet exist.

8. That Agentic OS is a client product
   Do not describe Agentic OS / TTROS as a SaaS, product, platform, or thing sold to clients. It is the internal operating system that runs TTR.

9. Prospect-specific facts we have not verified
   No invented familiarity, urgency, budget, tech stack, buying intent, pain, or interest signal.

10. False pretext
   No pretending there is shared history, referral context, prior interest, or a relationship hook that is not real.

Practical rule: every external claim should survive the question, “What is the source?” If the answer is “our interpretation” or “probably true,” phrase it as a hypothesis or don’t say it.
