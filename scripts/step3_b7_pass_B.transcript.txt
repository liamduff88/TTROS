--- Q3/25 [A3] How is delivery actually done?
    latency_s=22.3 manifest=/home/liam/agentic-os-live/queue/context_assemblies/hermes-20260906_172917_effa32-20260906_172917_effa32:d944494d-85ee-4153-8383-37d18e16b40c:351f24f4.json
    ANSWER: Delivery is not “advice then handoff.” It is forward-deployed implementation against the client’s real workflow.

The actual pattern is:

1. Scope
   Delivery starts only when there is:
   - a client/entity page
   - a signed or explicitly agreed scope
   - a client-isolated working folder
   - a clear definition of done

   If those are missing, delivery should stop. Otherwise you end up doing unpaid, unbounded consulting.

2. Map the real operation
   First delivery step is observing and mapping the actual workflow:
   - where leads/tasks/data enter
   - who touches them
   - where they stall
   - what tools are involved
   - what numbers matter
   - what approvals or human gates exist

   The output is usually a one-page map, not a huge strategy deck.

3. Diagnose one operational bottleneck
   TTR should identify the highest-leverage friction point:
   - speed-to-lead failure
   - missed follow-up
   - scattered client/team knowledge
   - manual routing
   - stale CRM/data
   - unclear owner/action/date after meetings
   - no visibility into what is working

   The discipline is: one workflow, one bottleneck, one fix. Not “transform the business.”

4. Design the target workflow
   Before building, TTR defines the new operating path:
   - trigger
   - capture
   - routing
   - response/follow-up
   - owner
   - system of record
   - approval gates
   - failure/rollback path
   - acceptance test

   Client sign-off matters before implementation, especially if the build touches live systems or external communications.

5. Build inside the client context
   Implementation can include scripts, automations, CRM config, knowledge-base structure, forms, lead routing, dashboards, SOPs, or AI-supported workflows.

   But the boundary is important:
   - read/draft-only unless external action is approved
   - no real sends without approval
   - no mixing client data
   - no unscoped build creep
   - no “AI magic” without source-backed evidence

6. Test with real acceptance evidence
   Delivery is not done because the artifact exists. It is done when the workflow proves it works.

   Examples:
   - Speed-to-lead: a test lead goes through every scoped inbound path within target response time.
   - Client memory: sample claims trace back to sources, and real business questions are answered correctly from the knowledge base.
   - Monthly AI ops support: session notes, actions, decisions, and summary are captured in the client hub within the promised window.

7. Handoff
   The client gets operational documentation:
   - what the system does
   - what it does not do
   - how to update it
   - how to pause or rollback
   - who owns each part
   - what to monitor next

8. Closeout
   TTR updates the client record, writes a receipt/evidence trail, records token/cost where required, and closes/revokes access where appropriate.

The commercial version is:

- Quick-Win Scan: diagnose one workflow bottleneck and prescribe one fix.
- Build: implement one scoped workflow improvement.
- Retainer: keep the client operating system current through recurring sessions, notes, actions, decisions, and recommended next builds.

My blunt read: delivery is strongest when it is boring and provable. The client should be able to say, “Before, this workflow leaked time/revenue here. Now it runs this way, and here is the evidence.” If we cannot point to that, we delivered theatre, not value.
