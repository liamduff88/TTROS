FINDING 2: cache_write_tokens was 0 on all 4 observed API requests, with no exception. Matches

point, never surfaced as an explicit write bucket the way Anthropic's is.
FINDING 3 (a genuine miss, reported plainly): calls 2 and 3 do NOT show a clean miss-then-hit
transition -- cache_read_tokens is IDENTICAL (8704) on both legs, not 0-then-8704. Two

queue/context_assemblies entries at ~17:50-17:55, same session run), so leg A was never a true
cold miss; and/or (b) the ~11,000 input tokens NOT covered by the cache_read figure (19899-8704)
include per-session volatile content (session_id, timestamps) that breaks prefix-identity between
the two legs before my SHARED_PREFIX filler is reached, so the filler itself was never inside the
cached region on either call. DOES NOT SETTLE which of (a)/(b) is the mechanism, or whether a true
cold-start miss (e.g. first call after an idle period) would show cache_read_tokens=0. Would need
1+ more calls with a verified-cold cache to isolate -- not spent, per budget discipline.
FINDING 4 (confirms P3 exactly): the raw provider usage object is ABSENT from the post_api_request
hook payload on all 4 requests (`raw_usage_key_present: False` throughout) -- by design
(run_agent.py explicitly pops `raw_usage` before handing the summary to hook subscribers). B8
therefore cannot log "the raw provider usage object" as the design of record's bounds literally
ask, from this attach point, without patching Hermes -- which header rule 9 forbids. What B8 CAN
and does log is the full normalised bucket set every request: input/output/cache_read/cache_write
/reasoning tokens, finish_reason, response_model, base_url, api_mode, and wall-clock
api_duration per call.
FINDING 5 (credential-awareness, bounded by header rule 1): B8 logs provider ("openai-codex"),
model ("gpt-5.5"), and base_url ("https://chatgpt.com/backend-api/codex") on every call -- this is
the "serving provider/model" the design of record asks for. It does NOT attempt to derive a
stable opaque credential-slot identifier, because the only place such an identifier could plausibly
be read (the profile's credential/token store, e.g. auth.json) is a protected boundary under
header rule 1 ("never read... any auth or credential store") -- not inspected, not opened, not
"checked for shape." The post_api_request hook kwargs carry no credential-slot field of their own
(full kwarg key list captured in the jsonl transcript). This is reported as a bound, not treated
as absence-implies-nothing: if a future step needs per-credential attribution, it needs a
sanctioned, non-file-reading source for that identifier (e.g. Hermes exposing one in the hook
payload itself), not a workaround that opens the credential store.
FINDING 6: latency (api_duration from the hook, the authoritative per-request wall-clock) ranged
2.354s-5.950s across the 4 requests -- inside the low-single-digit-seconds P4 prediction. No

prefill-bound, on these short replies) -- though Finding 3 means this comparison is confounded by
the flat cache_read_tokens across legs 2/3, so it is weak evidence at best, not a clean
cache-hit-vs-miss latency comparison.
